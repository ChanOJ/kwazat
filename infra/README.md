# Infrastructure

Scaleway, described with OpenTofu. Design and phases: [docs/infrastructure.md](../docs/infrastructure.md).
One-off manual steps: [bootstrap/README.md](bootstrap/README.md).

| Stack | Holds | State key |
|---|---|---|
| `shared` | Staging and prod projects, image registry, CI registry identity | `shared/terraform.tfstate` |
| `envs/staging` | Staging database, identities, secrets, jobs (module `modules/environment`) | `staging/terraform.tfstate` |
| `envs/prod` | Same module for prod | `prod/terraform.tfstate` |

Every command goes through `infra/tofu.sh`, which injects the secrets of `infra/secrets.env` from
Proton Pass:

```bash
pnpm infra envs/staging plan -out=staging.tfplan
```

```bash
pnpm infra envs/staging apply staging.tfplan
```

Plans are encrypted like the state and git-ignored; delete them after applying.

## What lives where

- **Database access**: two IAM applications per environment. `migrate` (ServerlessSQLDatabaseReadWrite)
  changes the schema; `runtime` (ServerlessSQLDatabaseDataReadWrite) reads and writes data only
  (checked on 2026-11-18: DDL is refused with `permission denied for schema public`). Their
  connection strings are the secrets `DATABASE_URL_MIGRATE` and `DATABASE_URL`, written by
  OpenTofu as write-only values. The API keys behind them are generated by OpenTofu, so they are
  in the (encrypted) state.
- **Third-party keys** (`ANTHROPIC_API_KEY`, `BRAVE_SEARCH_API_KEY`): OpenTofu declares the
  secrets; their values are entered by hand and never reach the state.
- **Jobs**: `kwazat-migrate` (runs `migrate`) and `kwazat-researcher` (default arguments: a free
  identity-only run; override them per run). OpenTofu creates them with the `image` of
  `envs/<env>/terraform.tfvars`; after that, CI owns their image (OpenTofu ignores it).
- **CI identities**: `kwazat-ci-registry` pushes images (registry of `kwazat-shared` only);
  `kwazat-ci-deploy-<env>` manages the jobs of its environment and reads the registry. Neither
  can touch IAM, secrets or the database, so CI does not run OpenTofu: infrastructure changes
  are planned and applied from a laptop.

## Owner steps

### Registry key for GitHub Actions (once)

From the repository root, logged in to `pass-cli` and `gh`:

```bash
infra/tofu.sh shared output -raw ci_registry_secret_key | gh secret set SCW_REGISTRY_SECRET_KEY --repo ChanOJ/kwazat
```

The key only goes from the encrypted state to GitHub; it is never displayed.

### Staging API keys (once, then on rotation)

1. Claude Console > **Settings** > **API keys** > **Create key**: name `kwazat-staging-jobs`,
   expiry **Custom**, about one year, scope **`kwazat-staging`**. Copy the key.
2. Scaleway console > project **`kwazat-staging`** > **Secret Manager** > secret
   **`ANTHROPIC_API_KEY`** > **Add version**: paste the key, then **Add**.
3. Same for **`BRAVE_SEARCH_API_KEY`**, with a Brave Search key (a separate key for staging if
   your Brave plan allows it).
4. Tell Claude: `api_keys_ready = true` goes into `envs/staging/terraform.tfvars`.

### GitHub environment `staging` (once, then on key rotation)

The deploy key is an **environment secret**: only jobs running in the `staging` environment,
from `main`, can read it.

1. GitHub > repository **Settings** > **Environments** > **New environment**: `staging` >
   **Configure environment**.
2. **Deployment branches and tags**: **Selected branches and tags** > **Add deployment branch or
   tag rule**: `main`.
3. From the repository root, the key and the project id (the key is never displayed):

```bash
infra/tofu.sh envs/staging output -raw ci_deploy_secret_key | gh secret set SCW_DEPLOY_SECRET_KEY --env staging --repo ChanOJ/kwazat
```

```bash
gh variable set SCW_PROJECT_ID --env staging --repo ChanOJ/kwazat --body "$(infra/tofu.sh envs/staging output -raw project_id)"
```

### Protect `main` (once)

GitHub > repository **Settings** > **Rules** > **Rulesets** > **New ruleset** > **New branch
ruleset**:

1. Name `main`, enforcement **Active**, target **Include default branch**.
2. Tick **Restrict deletions**, **Block force pushes**, **Require a pull request before merging**
   (required approvals: **0**, since you merge your own pull requests), and **Require status
   checks to pass** with `code` and `infra` (they appear once CI has run on a pull request).
3. **Create**.

## Deployments

Every merge to `main` (except documentation-only changes) runs **Deploy staging**: CI checks,
image build, then `infra/scripts/deploy-jobs.sh`, which points both jobs at the new image by
digest, runs `kwazat-migrate`, then a free identity-only `kwazat-researcher` run. A failed job
fails the workflow at once; network hiccups and platform interruptions are retried.

**Prod** is deployed by a version tag on a commit of `main` that staging already runs:

```bash
git tag -a v0.1.0 -m "First prod release" origin/main
```

```bash
git push origin v0.1.0
```

**Deploy prod** checks, without any secret, that the commit is on `main` and that its staging
deploy succeeded, then waits for your approval (GitHub > **Actions** > run > **Review
deployments** > **production** > **Approve and deploy**). It then points the prod jobs at the
digest built for that commit (the same image as staging), runs `kwazat-migrate` and the smoke run.
The `production` environment only accepts `v*` tags and holds its own deploy key.

To redeploy staging by hand: GitHub > **Actions** > **Deploy staging** > **Run workflow**. To run a job
by hand: Scaleway console > project `kwazat-staging` > **Serverless Jobs** > job > **Run job**.

## Key expiry

Scaleway gives API keys a one-year expiry. Keys created on 2026-11-18 expire on **2027-11-18**:

- database keys (staging): `pnpm infra envs/staging apply -replace='module.environment.scaleway_iam_api_key.database["migrate"]' -replace='module.environment.scaleway_iam_api_key.database["runtime"]' -var database_url_version=2`
  (raise the version each time, so the connection strings are rewritten);
- CI registry key: `pnpm infra shared apply -replace=scaleway_iam_api_key.ci_registry`, then set
  the GitHub secret again;
- the operator key (`scaleway-operator-*` in Proton Pass) is renewed by hand in the console.

## DNS and web front

`kwazat.fyi` and `kwazat.com` are registered at Infomaniak and delegated to Scaleway (project
`kwazat-shared`). Each environment runs a `web` Serverless Container (image built from `web/`:
Caddy serving the waiting page, `robots.txt` and `security.txt`) behind these names:

| Environment | Hostnames | Records |
|---|---|---|
| staging | `test.kwazat.fyi` (not indexed) | CNAME |
| prod | `www.kwazat.fyi` (canonical), `kwazat.fyi`, `kwazat.com`, `www.kwazat.com` (the last three redirect to `https://www.kwazat.fyi`) | ALIAS at the apex, CNAME for `www` |

Scaleway issues the certificates. `infra/shared` also publishes `v=spf1 -all` and a `p=reject`
DMARC record on both domains, and a null MX on `kwazat.com`, until mail is set up (phase 6).

Setting it up, in order:

1. Register both domains as external domains in `kwazat-shared` (done on 2026-11-18 through the
   API) and add their `_scaleway-challenge` TXT records at Infomaniak (done on 2026-11-18).
2. As each domain is validated in Scaleway: add it to `dns_ready_zones` in
   `infra/shared/terraform.tfvars` and in both environments' `terraform.tfvars` (with
   `web_image` from the Image workflow), then plan and apply. Do it **before** switching its
   name servers: the new zone is otherwise empty and the domain loses its records.
3. At Infomaniak: replace the name servers of both domains with `ns0.dom.scw.cloud` and
   `ns1.dom.scw.cloud`.
4. GitHub environment variable `WEB_URL` (`https://test.kwazat.fyi` for `staging`,
   `https://www.kwazat.fyi` for `production`), so that deploys check the public names too.

Later web images are deployed by CI (`infra/scripts/deploy-web.sh`), like the jobs.
